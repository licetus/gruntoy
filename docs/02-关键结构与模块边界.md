# 02 · 关键结构与模块边界

> 本文是理解代码组织的主文档。目标：让接手的人能在 15 分钟内知道
> **哪个行为该改哪个文件、哪些东西不该动**。

---

## 1. 总体分层

固件分为四层，依赖方向严格单向向下，不存在反向调用：

```
┌──────────────────────────────────────────────────────────────┐
│  L4  入口层      gruntoy.ino                                 │
│      setup() / loop()；唯一持有 Preferences 句柄               │
├──────────────────────────────────────────────────────────────┤
│  L3  交互层      cli.cpp        （编译期可整体移除）            │
│      串口命令解析 → 参数读写 / 体感测试 / 状态注入              │
├──────────────────────────────────────────────────────────────┤
│  L2  逻辑层      mood.cpp   心情值引擎：状态机 / 闸门 / 链路    │
│                  tail.cpp   摇尾通道：档位 → 频率幅度 → 过渡    │
│                  haptic.cpp 体感引擎：呼吸 / 咕噜 / 扫频 / 提示震│
├──────────────────────────────────────────────────────────────┤
│  L1  数据层      params.cpp 参数表 / 校验规则 / NVS 持久化      │
│                  config.h   引脚与编译期开关（唯一硬件常量处）   │
└──────────────────────────────────────────────────────────────┘
```

**为什么不把逻辑塞进 `.ino`**：`.ino` 只做装配。所有可测的逻辑都在 `.cpp` 中，
且不依赖 Arduino 之外的运行时——这正是 `test/` 能用桩文件在电脑上跑起来的前提。

## 2. 模块职责边界

| 模块 | 负责 | **明确不负责** |
|---|---|---|
| `config.h` | 引脚、PWM 载波参数、编译期开关、NVS schema 版本 | 任何**行为**参数（→ `params.cpp`） |
| `params.*` | 75 项参数的存储/钳制/校验/持久化/预设 | 任何执行动作（不发 PWM、不改状态机） |
| `mood.*` | 心情值、6 态状态机、闸门、呼吸触发链路、摇尾档位决策 | 具体波形（→ `haptic`）、具体摇尾输出（→ `tail`） |
| `haptic.*` | 震动波形：呼吸包络、咕噜调制、扫频、提示震、通道互斥 | 心情值语义、档位语义 |
| `tail.*` | 档位 → 频率/幅度 → 平滑过渡 → 输出 | **机构选型、连杆、限位标定**（属选型清单） |
| `cli.*` | 串口解析、参数读写入口、调试态注入 | 任何业务判定（一律转调 L1/L2 接口） |

### 2.1 三个最容易越界的地方

**① `tail.cpp` 不碰机构。** 它只把档位翻译成「频率 Hz×100 + 幅度 ×100」，并保证切换平滑。
`ENABLE_TAIL_OUTPUT = 0` 时它**只计算不输出**。接机构是另一份执行清单的事——
本模块把接口留好，但不替机构做决定。

**② `haptic.cpp` 不认识「心情值」。** 它的入参是「呼吸档位 1~3」或「咕噜时长 ms」，
是纯执行器。把心情值语义漏进 `haptic` 会导致它无法被单独测试。

**③ `params.cpp` 不执行任何动作。** 它只回答「这个值合法吗」「现在是多少」。
`SET` 命令改参数后立即生效，靠的是 L2 每次 `tick()` 都重新读参数，
而不是靠写参数时推送事件——这让「参数即配置」这件事保持简单。

## 3. 三层配置架构

```
        优先级高
   ┌─────────────────┐
   │ 云端下发配置     │  ← v1.0 仅留接口，config_cloud_enabled 默认 0
   └────────┬────────┘
            │ 拉取成功才覆盖
   ┌────────▼────────┐
   │ 本地 NVS 配置    │  ← Preferences，命名空间 "gruntoy"
   └────────┬────────┘
            │ 存在且 schema 匹配才覆盖
   ┌────────▼────────┐
   │ 硬编码默认值     │  ← params.cpp 的 META 表
   └─────────────────┘
        优先级低
```

### 3.1 关键约束：拉取失败必须保持本地值，禁止回落硬编码

这是三层架构里唯一容易被写错的地方。常见错误实现是「云端拉取失败 → `return;`」之后
参数已被重置为默认值。正确语义是：**失败什么都不做**，当前值原样保留。

`Params::getLayerName()` 会如实报告生效值来自哪一层（`默认 (hardcoded)` /
`本地 NVS` / `云端`），`info` 命令即可核查。

### 3.2 NVS schema 版本守卫

`config.h` 的 `PARAMS_NVS_SCHEMA`（当前 `2`）与 NVS 中记录的版本比对，
**不匹配则忽略整份旧 blob 并回落默认值**，而不是按新布局去误读旧数据。

```cpp
// params.cpp save()：版本号与配置数据一起写入
prefs.putUInt("ver", PARAMS_NVS_SCHEMA);
prefs.putBytes("cfg", s_v, sizeof(s_v));

// load()：版本不符 → 直接放弃，不使用旧 blob
if (ver != PARAMS_NVS_SCHEMA) return false;
```

> **升级提醒**：v1.0 的 schema 为 `2`，与 PoC 不兼容。首次烧录建议先 `RESET ALL` + `SAVE`。
> 未来任何参数增删都必须 `PARAMS_NVS_SCHEMA + 1`，否则旧 blob 会被按新布局误读。

## 4. 体感状态机（PRD §9.5 六态）

### 4.1 状态与迁移

| 状态 | 含义 | 迁移条件 |
|---|---|---|
| `ACCUM` | 待机 / 累积中 | 抚摸累积至阈值且闸门开放 → `PURR` |
| `PURR` | 咕噜中 | 锁定时长 `m_purrTargetMs` 到达 → `LANDING` |
| `LANDING` | 降落中 | `P-15` 到达 → `COOLDOWN` |
| `COOLDOWN` | 冷却中 | `P-20` 到达 → `ACCUM` |
| `LOWPOWER` | 低电（占位） | 优先级最高，可打断任意态 |
| `UPGRADING` | 升级（占位） | 优先级最高，可打断任意态 |

主循环闭环：`ACCUM → PURR → LANDING → COOLDOWN → ACCUM`

### 4.2 三条不变量

1. **所有状态切换必经 `enterState()`** —— 保证 `m_stateStart` 与副作用（计数、计时器复位）
   同步。绕过它直接改 `m_state` 会导致时长判定错乱。
2. **进入 `COOLDOWN` 时记录 `m_lastPurrEndMs`** —— 这是 `P-30` 轮次间隔闸门的唯一计时基准。
3. **`LANDING` 期冻结衰减** —— 冷却与降落不受自然衰减影响（FR-37c）。

### 4.3 摇尾档位与状态的联动

| 状态 | 摇尾档位 | 说明 |
|---|---|---|
| `PURR` | **锁 W4** | FR-39 验收要求，不依赖迟滞判定 |
| `LANDING` | 按心情值 + **用 `P-52` 时长**缓降 | 与心情降落时长对齐（`C-16` 强制差异 ≤ 1s） |
| `ACCUM` | 按心情值 + `P-50` 迟滞 | 防档位边界抖动 |
| `LOWPOWER` / `UPGRADING` | 停摆 | 安全优先 |

## 5. 交互优先级（`onStroke()` 判定顺序）

抚摸事件的判定顺序即为优先级，**顺序本身是设计的一部分**：

| 序 | 状态/条件 | 处理 | 反馈 |
|---|---|---|---|
| 1 | 任意 | 重置摇尾「无互动停摆」计时 | — |
| 2 | `PURR` | 直接返回，**不叠加** | 无（咕噜正在进行） |
| 3 | `LANDING` | 不计分（`P-19` 控制） | 柔震 `P-18`，占空比取 L1 |
| 4 | `COOLDOWN` | 不计分 | 拒绝震 `P-21`，占空比取 L2（**比柔震更重**） |
| 5 | `LOWPOWER`/`UPGRADING` | 不受理 | 无 |
| 6 | `ACCUM` + 防抖 | 过快重复被过滤 | 无（可经日志观测） |
| 7 | `ACCUM` + 有效 | **计分** → 可能触发咕噜 | 咕噜或呼吸 |

### 5.1 首次抚摸不做防抖判定

`m_everStroked` 标志：开机后第一次抚摸无条件响应。

**为什么**：`init()` 时 `m_lastStrokeMs = 0`，若用户开机后 500ms 内（`P-06`）就摸一下，
按纯防抖逻辑会被过滤——用户得到的第一印象是「这玩具没反应」，而且不会摸第二下。
这是产品语义要求，不是迁就测试。

### 5.2 降落期与冷却期的反馈必须可区分

| 场景 | 时长参数 | 占空比 |
|---|---|---|
| 降落期（还在「享受」） | `P-18` 默认 200ms | L1（默认 25%，轻） |
| 冷却期（「累坏了」） | `P-21` 默认 300ms | L2（默认 40%，重） |

两者都「感受得到」，但强度不同。若省略反馈，用户判定玩具失灵（PRD §12 异常 22）。

## 6. 咕噜的两道闸门（FR-36 ⑤⑥）

咕噜不是「到阈值就无限触发」，受两道闸门约束，避免玩具「停不下来」：

| 闸门 | 参数 | 语义 | 观测 |
|---|---|---|---|
| 轮次间隔 | `P-30` 默认 15s | 距上一轮咕噜**结束**不足 15s 不放行 | `purrGateState() == PG_GAP` |
| 累计上限 | `P-31` 默认 300s | 近期累计咕噜运行达上限 → 锁定，须休息 `P-30` 以上才解锁 | `PG_CUMULATIVE` |

`purrGateState()` 为**只读观测接口**，不改变任何状态，`status` 命令即显示它。
被闸门拦下时，状态机不进入 `PURR`，但会正常更新摇尾档位（避免档位卡住）。

## 7. 呼吸触发链路（FR-35 / §9.6）

呼吸不在固定周期自动起，而是由**抚摸事件**触发，条件全部满足才启动：

| # | 条件 | 参数/来源 |
|---|---|---|
| 1 | 状态为 `ACCUM` | 咕噜/降落/冷却期不起呼吸 |
| 2 | 震动通道空闲 | 非咕噜、非扫频、非呼吸 |
| 3 | 距上次呼吸 ≥ 最小间隔 | `P-43` 默认 30s |
| 4 | 档位由心情值决定 | `P-44`/`P-45`/`P-46`（L1/L2/L3 峰值占空比） |

### 7.1 链路顺序：先咕噜判定，后呼吸

`onStroke()` 里 `maybeTriggerBreath(now)` **在咕噜判定之后**调用。

**原因**：如果本次抚摸直接触发了咕噜，状态已切到 `PURR`，此时呼吸会被互斥规则挡下。
若把呼吸放在前面，就会出现「先起一次呼吸、随即被咕噜抢占」的无效启停——
听觉上是一次多余的抖动。顺序调整后，这类启停不再发生。

## 8. 体感引擎的互斥与优先级

| 优先级 | 模式 | 说明 |
|---|---|---|
| 高 | `HM_PURR` / `HM_SWEEP` | 咕噜与扫频互斥，**不可被提示震打断** |
| 中 | `HM_BREATH` | **可被提示震打断** |
| 低 | `HM_BARE` | 裸测，长转，供 Day2 测起转阈值 |
| — | `HM_BUZZ` | 短促提示震（柔震/拒绝震共用），用完回到原模式或 IDLE |

`startBreath()` / `startSweep()` 返回 `bool`，被互斥挡下时返回 `false`，
调用方可据此判断并给出提示，而不是静默失败。

## 9. 门控调制：让 `P-32` 真正落到输出

这是 v1.0 相对 PoC 最实质的一处补齐，单独说明。

### 9.1 问题

马达的 PWM 载波固定为 20kHz（高于人耳敏感区，抑制载波啸叫）。
但「咕噜的驱动频率」（`P-32`，默认 30Hz）与载波频率是两个完全不同的概念：
载波决定「怎么驱动」，驱动频率决定「以多快的节奏一顿一顿」。

PoC 中 `P-32` 只被读进变量、从未影响输出——于是「扫频 25→50Hz 找猫感区间」
这项 M1 核心实验在物理上没有任何差异。

### 9.2 实现

在每个 `1/f` 周期内，按目标平均占空比切成「导通 / 断开」两段：

```cpp
const uint32_t periodMs = 1000u / freqHz;         // 30Hz → 33ms
const uint32_t onMs     = periodMs * dutyPct/100; // 65% → 21ms 导通
const uint32_t phase    = elapsedMs % periodMs;
applyDuty(phase < onMs ? 100 : 0);                // 满量程或完全断开
```

效果：**平均功率与目标占空比一致**，同时在 `f` 上产生可听的震颤——这才是「咕噜」。

### 9.3 三条边界

| 情况 | 处理 | 理由 |
|---|---|---|
| `duty <= 0` | 直接输出 0 | 避免除零，且语义即「停」 |
| `freq == 0` | 退化为纯 PWM（不门控） | 频率为 0 时门控无意义 |
| `duty >= 100` | 直接输出满量程 | 全程导通，无切换 |

### 9.4 如何验证它真的生效

`test_haptic.cpp` 用两条互补断言把「是否真的落到输出」钉死：

1. 输出样本**只含 0 与满量程**两种值（证明是切脉冲，而非模拟包络）；
2. 同样时长内 **50Hz 的通断切换次数显著多于 20Hz**（证明频率参数真实生效）。

对照：呼吸**不使用**门控调制（走纯 PWM 正弦包络），因此呼吸测试断言的恰好相反——
中间值样本必须占 80% 以上。这两组相反的断言互为交叉验证。

## 10. 非阻塞约定（全局）

`loop()` 内只有四件事，全部非阻塞：

```cpp
void loop() {
  g_cli.poll();      // 串口逐字节收 + 自动抚摸调度
  g_haptic.tick();   // 震动包络与门控推进
  g_mood.tick();     // 状态机推进
  g_tail.tick();     // 摇尾过渡推进
  delay(1);          // 让出 CPU，降低空转功耗
}
```

**禁止在任何 `tick()` / `poll()` 路径中调用 `delay()`。** 一旦阻塞，咕噜时长、
降落曲线、冷却计时全部停摆——PoC 的 `t feed` 用 `delay(1200)` 阻塞，导致
「喂入期间观察降落是否平滑」这件事根本观察不到。v1.0 的 `t feed` / `t auto` 改为
基于 `millis()` 的调度（`m_autoNextMs`），并在测试中用「馈入期间状态机仍能推进」断言守住。

## 11. 数据流一图

```
  抚摸事件                          串口命令
  onStroke()                       SET / t feed / PRESET
      │                                  │
      ▼                                  ▼
  ┌─────────────┐  读参数   ┌──────────────────────┐
  │ mood.cpp    │◄─────────►│ params.cpp（75 项）   │
  │ 状态机+闸门  │  写参数   │ 校验 C-01~C-18/X-01~03│
  └──┬───────┬──┘           └──────────┬───────────┘
     │       │                          │ SAVE/LOAD
     │       │                          ▼
     │       │                    NVS (Preferences)
     │       ▼
     │  ┌──────────────┐   档位决策
     │  │ tail.cpp     │◄── W1~W4 → 频率/幅度 → ease-in-out 过渡
     │  └──────┬───────┘
     ▼         ▼
  ┌──────────────────┐
  │ haptic.cpp       │  呼吸包络 / 咕噜门控 / 扫频 / 提示震
  └────────┬─────────┘
           ▼
      ledcWrite(MOTOR_PWM_CHANNEL) → GPIO25
```

> 注意：`mood.cpp` 是唯一同时「读参数 + 改状态 + 调执行器」的模块，因此它也是
> 唯一需要 `HapticEngine*` 与 `TailDriver*` 两个依赖注入的模块（`init(haptic, tail)`）。
> 其余模块之间无耦合，可单独测试。
